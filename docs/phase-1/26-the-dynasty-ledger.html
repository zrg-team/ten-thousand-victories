The flow being built

The one rule that keeps this honest

Waves shadow the realm's power (dossier §03), so traits are verbs, options and tempo — never raw power. The published budget: all stat-flavoured traits together ≤ +10% power equivalent, and flat resource seeds land only inside waves 1–5 where EARLY_WAVE_FIELD_SHARE already caps the enemy. Write this cap as a comment at the top of the trait table so future content keeps the promise.

Design notes the master dossier had no room for: the level-up offers two of the un-owned traits, rolled, no reroll — a pick must be a fork, not a menu; the sheet finally says the ancestral code out loud (it has been silently applied since the codes feature shipped — the best-earned carry-over in the game was invisible); and the next-reign screen shows Phase 3/4's empty rows from day one, so the player sees the shape of what's coming. Respec: one full respec per ascension, none casually — traits are a biography, not a loadout.

04

Implementation steps

  1. The store. src/state/dynasty.ts modelled line-for-line on legacy.ts: versioned key, defensive shape-checked parse, getDynasty / addRunXp / chooseTrait / hasTrait. addRunXp(score) returns how many level-ups it produced. new src/state/dynasty.ts · pattern: src/state/legacy.ts
  2. The trait table. src/data/dynastyTraits.ts — the eight above with the budget comment. i18n keys dynasty.trait.<id> and .d in both en and vi — a missing key crashes the game at import time; this is the repo's hardest invariant. new src/data/dynastyTraits.ts · src/i18n/catalogs/ (en + vi)
  3. Wire the six live read sites. Draft size, reroll price, founder count, doctrine slot, muster ticks, start seed — each a hasTrait(...) read at the site named in the table. Nothing else changes. PowerDraftSystem.ts · AscentState.ts · MusterSystem.ts · createAscentGameState (GameState.ts)
  4. The ceremony chain. New prompt kind dynasty-level (two trait options, pick one). endAscentRun banks XP via addRunXp(computeRunScore(state)) and, if picks are pending, queues dynasty-level prompts before the existing run-over. Resolver case in AscentResolver; prompt signature in constants.ts; renderer beside the run-over page. Bind/swear steps registered as no-op pass-throughs for Phases 3–4. src/systems/ascent/AscentResolver.ts (endAscentRun) · src/scenes/conquest/prompts/run.ts · src/scenes/conquest/constants.ts
  5. The dynasty sheet. A menu page: founder portrait (the layered wardrobe system — promote the rank badge with dynasty level so the king visibly ages), level + XP bar, reign count, owned trait chips. Follow InkUI conventions — cards auto-fit by measured height, notifications only in the header strip. src/scenes/MenuScene.ts (beside the Legacy page at ~line 2664)
  6. The next-reign screen. The run-over exit routes through a pre-run summary — founder pick (5 wide with the trait), owned traits on display — then starts the run. "Go again" must visibly mean "go again with". src/scenes/conquest/prompts/run.ts exit path · MenuScene start flow
  7. The harness. verify-dynasty.mjs, headless: seed a store → end a run → assert XP banked and a dynasty-level prompt raised → choose → new run's draft offers 5 cards. Add the new prompt kind to the option shapes the harness helpers know, or every later harness wedges on it. new test_scripts/verify/verify-dynasty.mjs · pattern: game-harness skill

Traps

  • Never route ceremony prompts through the decision director — its per-kind cooldowns and the court-phase window would swallow or delay them. The run-over path is terminal and paused; stay on it.
  • autoDefend and harness autopilots hide prompts — the dynasty harness must drive prompts explicitly, not wait for them.
  • XP double-banking: endAscentRun is guarded by legacyBanked against re-entrant ticks; bank dynasty XP inside the same guard.
  • Dual-module HMR: a long dev session can hold two module instances of the store — full reload before judging persistence bugs.
